## 结论

本版可以交付一个有限的、单方 2–4 人陆地图共享计划。位置是用户记录，兵种是具体单位形态，任务是主动认领，前置是用户明确填写的状态，兵力/资源是否足够是另一项自报记录。四者必须独立，不能转成阵容评分或胜率。建议新路由 `#/team-plan`，固定封建/城堡/帝王三个计划阶段，第一版只含四种可选任务：侦察、破城、掩护、支援。

最大的复用陷阱：`productionBuildings` 能核对常规生产资格，不能证明所选形态升级已经完成；`effectiveProductionTechs` 会补齐前置，不能用于把玩家未勾选的研究显示为已完成。单位升级在本项目也不是普通 Tech：例如弩手24对应 `.dat` 科技100、劲弩手492对应237、游侠569对应265，但这些升级不在 `techs.json` 中。

## 建议冻结的数据模型

以下是可实现的语义schema；命名可调整，但字段不得在分享时丢失。ID用稳定p1–p4，允许同文明多人，不能以文明名或当前数组下标指代玩家。每个阶段是“各玩家到达对应时代时的约定”，不表示大家在同一游戏秒数同时升级。

```ts
type PlanAge = 2 | 3 | 4;
type PlayerId = 'p1' | 'p2' | 'p3' | 'p4';
type TaskKind = 'scout' | 'breach' | 'screen' | 'support';
type Position = 'unspecified' | 'flank' | 'pocket' | 'custom';
interface Player {
  id: PlayerId;
  name: string; // <=24字符
  civ: string; // Civ.en，未知值恢复后保留并报错
  position: Position;
  positionNote: string; // <=48字符，如左边/中间/地图自定义
}
interface Force {
  unitId: number;
  buildingId: number; // 选定生产地点，不自动当建筑现成
}
interface PlayerPhase {
  playerId: PlayerId;
  main: Force | null;
  secondary: Force | null;
  completedBuildings: number[]; // 用户明确确认，默认空
  researchedTechs: number[]; // Tech目录中的已完成研究，默认空
  completedForms: number[]; // 已完成单位升级的形态ID，默认空
  supply: 'unchecked' | 'self-reported-ready' | 'self-reported-short';
  supplyNote: string; // <=120字符，仅用户记录，系统不认证足够
}
interface Task {
  kind: TaskKind; // 数组中出现即用户选择本阶段需要该任务
  owners: PlayerId[]; // 0–4人；同一任务可由两侧各一人认领
  intentionalGap: boolean; // 不因空owners自动打开
  gapReason: string; // <=120字符
  note: string; // <=120字符，注明侧别/具体分工
}
interface Phase {
  age: PlanAge;
  players: PlayerPhase[]; // 每名现存玩家恰好一条
  tasks: Task[]; // 0–4条，同kind不可重复；未选择的不检查
  supportTrigger: string; // <=160字符
  rally: string; // <=160字符，集合地点/条件
  retreat: string; // <=160字符，撤退约定
  notApplicable: string; // <=160字符，不适用条件
}
interface TeamPlan {
  version: 1;
  patch: 185872;
  title: string; // <=80字符
  map: { name: string; openness: 'unspecified' | 'open' | 'closed' | 'mixed-land'; conditions: string };
  players: Player[]; // 2–4人
  phases: [Phase, Phase, Phase]; // age依次2、3、4，全阶段总是入URL
  activeAge: PlanAge; // 当前查看阶段也可刷新恢复
  example: null | 'open-land-4v4-v1'; // 不可编辑来源注册项，仅演示计划身份
}
```

有限性建议：每玩家每阶段2个兵种、最多8个已建建筑/32个已研究科技/16个已完成形态；文本上限为输入规则，不能编码时截断。若实现上只提供“相关前置已完成”勾选，也必须把它持久化并明确具体前置，不得用选择单位本身代替完成确认。

位置行为：初始全部“未指定”。常见3v3两边一中、4v4两边两中只能当帮助文字/显式套用的例子。2v2不强制存在口袋位，也不应禁止用户记为口袋位。地图名称、开阔程度、位置均不自动生成任务或评分。位置不随文明改变。删除玩家是明确操作：只清理该玩家的阶段行与认领，保留其余玩家稳定ID；显示哪些任务变成尚未分配。人数低于2时禁删。损坏链接中的悬空认领必须报错，不默默转移给同序号别人。

## 合法性分层与状态优先级

结果建议返回 `issues[]`，每条带 `path` 与 `code`，不用单一队伍总分/通行灯。单位资料核对和任务分配分两块显示；合法兵种无需任务、有人认领的任务可以兵种为空，这两种都能保存/分享/打印。

1. **未指定**：main/secondary为空。显示“未指定兵种”，不会自动替换成标准弓骑，也不是必败。
2. **链接/引用无效**：未知ID、未知文明、悬空玩家、非法枚举等。保留可编辑语义对象并显示具体原因；类型破坏/未知版本另走锁定错误页。
3. **暂未支持**：队友特殊授予、限量雇佣、聚落生产等尚未编码的路线。即使静态常规树不可用，也不能把已知潜在队友解锁一律标成“游戏不允许”。提示“常规科技树无此路线；队友特殊解锁暂未支持”，附加成来源页。不因拥有来源文明而自动判定解锁完成。
4. **该文明不可用**：常规目录civs与文明树格不同时允许；已知特殊路线先按上项处理。不能把树缺格的undefined当成可用。
5. **时代未到**：使用该文明有效单位时代与有效生产建筑时代，不只读Unit.age。例如库曼封建攻城锤应可核对，普通文明封建骑士不可。
6. **尚缺前置**：分项列出建筑未确认建成、形态升级未完成、生产解锁研究未完成。`from_ !== null` 的形态，需要明确确认该形态及升级链；例如劲弩492需要弩手24与劲弩492两项完成，不能勾劲弩后自动把弩手算已完成。升级链设循环/深度保护。
7. **资料条件合法（按填写状态）**：只说明在固定数据与玩家填写的建筑/研究/升级条件下有合法路线。旁边始终有“兵力与资源是否足够：未核对/玩家自报”的独立文字。

已研究科技本身也校验时代、文明与Tech.pre；缺前置就报尚缺前置，不能调用会补全的`effectiveProductionTechs`冒充用户完成。仅在固定数据能明确证明自动/免费解锁且所有触发条件已成立时，才可单独显示“数据确认自动获得”，与用户勾选分列；首版宁可维持显式确认，不做自动全科技。

注意 `productionBuildings` 内部仍调用了自动补前置函数：本工具可将它用于**候选路线验证**，但最终前置完成必须单独使用显式集合校验，不能仅看其非空就输出就绪。普通兵种升级不能混进普通`researchedTechs`（升级tech100等不在Tech目录）。

已核对的特殊边界：近卫军759/761可在城堡生产；兵营需无政府16，不能一律说近卫军不合法。答刺罕886/887在城堡可产，马厩需掠夺者483。波希米亚城堡火枪手5仍需显式化学47。弗拉芒民兵1699原始Unit.age为2，但生产需帝王科技755，不能因目录时代而显示封建就绪。队友意大利佣兵882、热那亚骑兵1010/1012、帝王掷矛手1155、库曼雇佣相关1260应在未知接收端路线时标暂未支持；`team_bonuses.json`对越南目标关联仍为unknown，不可臆测完整映射。聚落路线仍沿用`production`已知未支持边界。

任务状态独立推导：owners非空为“已认领”（只代表约定）；owners为空且intentionalGap真为“有意留空”，展示原因；其余为“尚未分配”。未选择任务不检查。若任务owners非空且intentionalGap真，明确提示冲突供用户改，不静默改写。骑士、长枪、冲车等存在都不能自动认领任何任务，不输出“已具备反制/缺攻城必败/阵容不完整”。

## URL、刷新、分享与打印

- 无后端。建议 `#/team-plan?pv=1&plan=<base64url(UTF-8 JSON)>`，或沿现有market使用版本化JSON；采用base64url是为中文字段缩短链接，不是加密。固定键顺序、阶段顺序、集合排序以便往返稳定；数组玩家顺序和文字内容必须保留。
- URL包含整个快照：所有玩家、重复文明、位置、三个阶段的主副形态和生产地点、全部明确前置、全部任务/owners/有意留空理由、支援/集合/撤退/不适用文本、自报资源兵力、当前阶段、地图条件与示例标识。复制只复制activeAge不合格。
- URL是唯一分享真相，不能叠加接收者localStorage/sticky。裸入口初始化两名玩家与空三个阶段；任一编辑写完整快照。不得依赖浏览器里未分享的本地草稿恢复链接所缺字段。页面读取URL不自动写回，不因加载顺序变换计划。
- 正常编辑可replace URL；显式载入示例/打开另一方案用push，前进后退由location重解码恢复，不用闭包里的旧state。数据未加载前显示加载，不能把未加载的ID判未知而清空。
- 完整解码严格校验重复参数、未知版本、无效percent/base64/UTF-8/JSON、对象字段类型、schema完整性、人数/数组上限/文本上限、安全整数与深度。限制解码原文48KiB和编码token64KiB；先限制输入后JSON.parse。此大小是应用防护上限，不能宣称所有聊天软件都接受。
- 字段合法但实体/配置无效：保留原值和行并显示错误，允许修复；不能静默替换文明/单位、删除未研究项、丢失非当前阶段。结构损坏/未知版本：展示原链接、明确“链接无法完整恢复，尚未载入计划”，提供重置；禁止把默认计划显示成已恢复结果。错误链接不自动覆盖。
- 对所有受支持文本/数组组合做编码长度边界测试；若受限体积确实超出，必须在录入时明确拒绝并保留可复制原文/草稿，绝不截断后宣称复制成功。不要简单照搬teamBonuses的4096字符限制。
- 分享失败沿用手动复制完整链接；成功状态使用role=status。文本用React正常转义，不能插入innerHTML。打印不出现编辑输入；单独静态打印视图打印三个阶段及全部说明/来源/有意空缺，`textarea`不可仅打印可见高度。`break-inside:avoid`用于卡片，超长内容允许整块自然分页。
- “一页计划”应理解为一个可分享/打印的页面。用户把所有允许字段填满时，A4一张纸无法同时保证12px字体和不截断；冻结规格要明确为默认精简示例可在一页、长自填内容允许多页，不能缩字或裁剪来满足字面一页。
