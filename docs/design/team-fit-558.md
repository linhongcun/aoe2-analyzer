## 玩家任务与范围

开房选文明前，先选自己想玩的候选，再加入 0–3 名已定队友，查看候选带来的团队来源、队友反向关联及具体兵种选择。页面不算胜率、阵容分数、总倍率、当前军队或实际分工。

建议路由 `#/team-fit`，名称“文明搭配”。在页面登记表中放 `planning / secondary`，使用现有 `users` 图标，靠近“团战分工”。首页、工具菜单、搜索沿登记表派生；队伍加成与团战分工可添加“选文明前看搭配”入口。

首版比较**完整科技树潜力**，不增加当前时代选择器。首屏只用一行“完整科技树潜力 · DE 188329 · 编辑口径，非官方推荐”；兵种区补一句“实际出兵与分工仍需另行约定”，研究和解锁的条件在对应条目附近呈现。避免用一整屏免责声明挡住选择任务。

## 结构与交互

1. 页首：标题、短任务句“先选候选，看它和队友有哪些关联。”以及一行口径。
2. 选择区：左/上为“你的候选”；右/下为“已选队友”。无参数严格 0 队友、候选待选。只显示已选队友与一个“加入队友”入口，最多 3 名；不先摆三位虚构玩家。候选未选时不输出比较结论。
3. 候选选好：PC 上并排“候选带来的团队来源”和“队友也能关联到候选”。单向没有内容时用简短说明，保留另一侧；不凑对称卡片。
4. 下一节“兵种选择多了什么”：方向、队友已可提供、候选可补充。突出具体新形态或路线；已有形态保留中性标签。窄屏按方向堆叠，保留两侧文字标题，不横滑。
5. 底部：复制搭配链接、查看完整队伍加成、带入团战分工。依据实际配置启用；无候选不分享，实际总人数不足 2 时不进入分工。

正式版复用 `CivPicker`，支持中英文检索、键盘、Esc 与焦点返回。候选可清空；队友可移除，重复文明合法。清空候选保留已选队友，先选队友也不自动生成候选。每次离散提交的候选或队友增删改使用 push 历史，使前进/后退能恢复上一份配置；picker 搜索等暂态不进入 URL。只有 canonical 整理或明确重置使用 replace。重置清空实际配置，不改成示例；示例不是必需功能。

静态线框中的空配置/已选阵容为不同的审阅示意，不属于产品的场景切换功能。正式页面复用选择器并按实际配置计算，不靠场景分支输出。

## 来源比较：同一潜力口径

真实数据与现有接口：`team_bonuses.json` 的 `permanent` / `technologies`、`teamBonusSources`、`teamTargetMatch`、`civStatus`、`unitRoles`、`collapse`、`upgradeLine`。不按文案关键词猜目标，不从文明评分推角色。

`teamBonusSources` 当前按阵容提供者返回**全部常驻来源与可研究团队科技**，不按 `researched` 过滤；研究状态由另一函数处理。before / after 都按完整潜力构建，再分别对常驻来源和团队科技按来源身份差分。不能一边只算已研究、一边算可研究，把队友原有科技误算为候选新增。

- 新增：加入候选后才出现的来源。
- 已有：原队友已提供同一来源，保留新增提供者，但不新增一份效果。
- 不同来源分别列出，即使目标类似也不合并倍率。
- 来源身份只比较常驻 `source.id`、团队科技的科技ID；候选置首会让 `providers.player` 重编号，不能拿整行或提供者数组比较后误报新增。
- “需研究”与“常驻”分栏/分标签，新增团队科技不等于已经生效。全部研究/完成标记仍为空。
- 自己也在团队范围内。原说明从文明 `tb` 或科技 `desc` 取，不改写倍率或范围。
- `targetUnits` 为直接关联，`productionUnits` 为生产地点间接关联，`targetBuildings` 为建筑关联；界面区分性质。
- `teamTargetMatch` 只辅助 match/unknown/none 三态筛选，不代替 direct/production/unlock 的展示性质。生产关联不能反推普通解锁；例如土堡578的 `productionUnits` 也含特殊1260，不能因此把它放入普通训练线。
- `partial/unknown` 来源保留可见，显示已核对目标和待核实说明。缺少已核对关联不写成“没有效果”，原加成本身不因此变成“效果未知”。
- 覆盖标签常显，不能藏入条件折叠；当前柏柏尔开放、土堡、库曼常驻与库曼雇佣兵等 partial 都在卡片头标“部分已核对”。
- 数据保留 `engineVerifiedInPinnedBuild=false` 的边界。“同一来源只汇总一次、不计算重复倍率”是本站展示口径，不能改写为已在客户端实测团队科技不会叠加。

## 精确单位与条件

常规形态同时核对 `unit.civs` 和 `civStatus(...)['u'+id] === 1`。这仍不是当前可持续生产或已解锁的证明：团队科技特殊提供须另列，不能只看上述两个字段。

方向复用 `unitRoles`。反骑方向限定为生成数据里对“骑兵”的正额外攻击，用“对骑兵额外攻击”命名；不承诺实战必胜。同一形态可出现在多个方向，不把分类个数相加当兵种总数。

同一具体形态的不同生产地点先规范身份，再做新增差分；普通/精锐和升级路线只在差分之后做展示归并，具体形态仍可逐一打开。升级分支使用所选文明的可用性：不能把波斯萨瓦尔换成游侠，也不能隐藏法兰克新增的游侠选择。

不从通用 `u.age` 自造“当前可训练”结论。长矛兵、提前时代和研究解锁等细节已有例外；首版跨时代展示，精确解锁条件通过对应条目及详情查看。

### 正式投影与密度合同

线框中的固定示例只是层级和密度样本。正式版所有配置必须由同一份真实投影生成，不能根据 Franks/Berbers 等场景名分支输出一套手写结论，也不能为凑线框里的行数硬截断数据。

**具体形态的处理顺序固定如下：**

1. 逐文明核对原始对象资格，先识别特殊提供/开放 channel；普通清单排除团队UT特殊版1260，保留常规1231/1233。条件来源仍单列，不因这一步消失。
2. 对普通对象按**相同完整英文名 `unit.en`**规范生产地点别名，沿现有目录的 same-en 等价口径识别同一具体形态。每个规范形态保留全部 raw IDs、各生产建筑、提供文明/玩家及地点研究条件，供详情与来源目标匹配。不能只保留一个代表ID后丢掉其余地点。
3. 在 before / 候选 / after 的**完整规范具体形态集合**之间做差分。禁止先做 raw-ID 差分再对新增列表 `collapse`，否则只增加生产地点也会误报新兵种。
4. 差分后才按普通/精锐家族与升级路线做展示归并和密度控制。不能在差分之前调用完整 `collapse`、`baseOf` 或去掉 `Elite` 来压成基础家族，否则会吞掉真正新增的精锐形态。`Paladin` / `Savar`、`Cavalry Archer` / `Mounted Crossbowman`、`Kipchak` / `Elite Kipchak` 的完整英文名不同，继续分别保留。
5. 升级路线仍逐文明按自己的可用性展开，再映射到规范形态并合并展示；来源关联使用保留下来的 raw IDs 匹配，不能把规范形态身份替换成一套丢失原目标的新ID。

上述身份与生产地点反例的只读证据在 [形态别名事实审计](team-fit-558-shape-alias-review.json)，含固定输入文件指纹。它是设计期事实审计，不是已经执行的产品算法验收。

- 首版主区比较常见陆战方向：步兵、骑兵、弓兵、攻城，以及“对骑兵额外攻击”。从已核对形态按同一规则分类；先排除船只和非作战目录项，不把村民或海军一次铺满主表。僧侣、海军及其他超出这五个主方向的对象仍可通过来源目标/文明详情查阅，不据主表缺席声称阵容没有这些选择。方向范围在主区说明或“怎么看”中可见。
- 按完整规范具体形态集合先算候选新增，再做展示归并与折叠。每方向优先列候选新增的具体路线/形态，默认最多3条路线；超出时显示“查看全部新增”，完整结果可键盘展开，不能丢弃超出的新增。
- 已有选项默认最多2条精确代表路线，优先显示这些路线在各自文明内可用的终端形态；旁注“代表选项”，并提供“查看已有完整清单”。展开后能看到全部已核对形态及提供文明。代表与终端是归并展示，不是战力排名；不按主观强度挑“最佳”代表。
- 代表选择使用稳定规则（既有目录顺序、确定性的路线/形态顺序等），不随用户随意换人而冒出随机例子。普通/精锐和相同兵种的不同生产地点不得撑成多个默认条目；新增只有精锐等后续形态时标“新增形态”，整条精确路线此前没有才标“新增路线”。
- 每文明先用自己的 `avail` 展开 `upgradeLine`，再按路线与精确形态合并提供者。禁止对整队 union availability 只展开一次：该接口优先独特分支，会用波斯萨瓦尔1813遮住法兰克游侠569。
- 方向允许交叉。2700/2701在 `unitRoles` 中同时属于骑兵与弓兵，正式投影保留这种交叉；线框只用部分代表项控制密度，不构成某一方向的穷举清单。波斯已有骑射手39/474，所以法兰克2700/2701只能称“新增骑马弩兵具体路线”，不能称原阵容缺骑射手或新增了骑射手方向。
- 普通形态全局排除已确认的团队UT特殊提供版1260，并保留常规1231/1233；关联578等生产来源也不能将1260重新注入。解锁或特殊提供单列条件，与普通持续训练线分开。
- 某方向没有新增时保留简短“暂无新增形态”及已有清单入口；不推导“没有用”“缺兵”或已经分工。只有候选时不把“无队友”当作队友没有某种能力。

线框未穷举完整列表，也没有实现上述折叠算法。未来正式失败用例须用多文明、多路线和分支数据证明归并、截断提示与展开完整性，而不是只断言当前 mock 中几个名字。

### 页面局部加载与失败

当前 `useCore` / `useTrees` 只有 `load().then(set)`，没有 catch；不能直接复用后把一直为null说成已处理加载失败。新页局部调用公开 `loadCore`、`loadTrees`，用 `Promise.all`/catch区分加载、就绪与失败，不改全局hooks或数据缓存设施。同步 `civs` 与CivPicker始终可编辑，URL/选择保留；重载按钮刷新当前地址，不因失败替换候选。

catch范围必须覆盖页面模型的异步模块及其数据依赖：现有团队来源模块含同步raw单位依赖，不能让新页入口静态引入这些大数据后在组件挂载前失败，再宣称页内catch已覆盖。入口与URL codec只保留同步文明、轻量配置及type-only依赖；不能因桥接编码器静态导入团队来源模块，或结果组件静态导入团队数据/文案，再间接把raw单位带到入口。模型、桥接函数与重结果组件统一纳入页面局部可catch的异步加载；实体Link/Linked只在core成功后渲染。不修改共享hook或缓存实现来规避该问题。

受控chunk拒绝验收须从首次直达带配置URL开始阻断新模型或数据chunk，不能先成功加载再假装失败。须看到页内失败、选择不丢、无假零来源/假缺口，并能经可见重载恢复。此用例允许记录预期network failure，单独断言其范围；不能把它计作常态console/pageerror零错，也不能靠吞掉所有错误来通过普通页面检查。

### 特殊开放能力的识别

按已核对 `kinds.unlock` 识别开放channel，避免文明场景硬编码：当前永久来源为柏柏尔1010/1012、意大利882；团队UT为690至1260。开放说明、链接与时代/研究条件单列，不能先套盟友普通 `unit.civs` 与树格资格门禁而隐藏队友可获的条件能力。578是生产关联而非解锁；1380的kinds为economy，2569/2571仍是正常形态，不因被团队科技影响而误排普通清单。
