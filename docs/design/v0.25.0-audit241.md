## 现有逻辑审计

- `src/features/matchup/components/Matchup.tsx` 只接双方文明，`ratings.ts` 从敌文明 `ty` 静态标签给泛反制。`filterCounterUnits` 仅按 `units.civs` 过滤，不接实际敌军、时代、已研究科技、建成建筑。不得直接用于本项的立即执行资格。
- `src/domain/duel.ts` 明示忽略射程、走位、地形与特殊能力；同兵种群战也不是混编协同。建议仅链接 `/duel` 并标“查看局部单兵资料”；不从本卡自动预填满科技或显示整套胜负。
- `src/domain/production.ts` 的 `productionBuildings/productionUnits` 可复核固定数据中的文明、树格、单位/建筑时代和化学等解锁。它们不证明实际建筑已建成，也不保证 `UnitUpgrade` 的形态已经研究。
- `effectiveProductionTechs` 会补全可用的科技前置；不能把它补出的集合显示为玩家实际已研究。`productionTechs` 只收生产/经济相关子集，不能用它证明战斗科技如火炮术已完成。
- 单位形态可沿 `Unit.from_` 和树格第六字段检查前序关系；当前完成状态仍须玩家明确输入。不要只因最终科技树有该格就把升级形态当现有兵。
- 建筑存在状态与研究完成分开；研究已完成后原建筑可能被拆。推荐新增单位时看其实际训练建筑，推荐新科技时再看研究地点。不要把二者绑定为同一布尔值。

## 结构、路由与共享建议

同意根代理预案：独立 `/mixed-army` 页面、`src/content/mixed-army.json`、纯领域函数 `src/domain/mixedArmy.ts`、`src/features/mixedArmy/MixedArmy.tsx` 与 `mixedArmy.css`、`docs/MIXED-ARMY.md`、测试 `mixedArmy241`。`/matchup` 增入口，文案“混兵情境：按已看到的阵容选择分工”。根代理统一改路由、导航、公开规格与 CHANGELOG，避免并行改公共文件。

最低输入契约建议：情境；自方文明；当前时代；场景/模式（Arena情境为1v1 Arena）；现有主力的准确形态或“其他/未知”；实际敌军主力与掩护组合（含未知与其他）；战车/火炮形态；开阔/狭窄/未知；侧向到场及撤回 `clear/blocked/unknown`；保护射击点与退路 `safe/unsafe/unknown`；食物与木金持续能力各 `sustainable/tight/unknown`；建筑及所需形态/科技完成状态。

前置状态可按卡汇总成“已具备/未具备/未知”，但必须展示所确认的具体清单，不能用含糊的“准备好了”覆盖文明或时代错误。精确的共享 readiness 字段由根代理与 `readiness_design_review` 冻结；本审计不更改公共生产模块。

结果至少分清 `ready`、`needs-observation`、`needs-preparation`、`age-unavailable`、`civilization-unavailable`、`not-covered`、`invalid-link`。未知不是“无护军”、资源够或安全；缺时代不是未覆盖；文明无法训练不是时代未到。合法的其他文明显示“本情境暂未整理该文明”，不显示“没有应对方法”。

分享采用 HashRouter 内 `#/mixed-army?...`，带 `mv=1` 与 `build=185872`，保存全部输入及 readiness。方案卡是纯函数派生，不持久化推导结论；若有用户选中的卡，也需恢复其 ID。无参数可用默认“全部关键观察未知”，有参数则必须完整且合法。缺键、重复键、未知键/版本、未知单位或非适用枚举、非法UTF-8、过长参数一律停推导并显式重置；不能静默使用默认后当已确认局面分享。浏览器回退、刷新、复制失败的手动完整链接都需覆盖。

不要使用 localStorage 盖过链接状态；现有 `castleDefense.ts` 的严格解码和 `sharePageUrl` 可作为模式。构建号不匹配显示版本不匹配并暂停，不自动当成当前数值。
