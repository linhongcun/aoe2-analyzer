# 游戏分析师交接

给以深度用户与《帝国时代 II：决定版》领域专家视角使用本站、共创文明策略与压测计算工具的人。角色定位与分工以 [CONTRIBUTING「角色」](../CONTRIBUTING.md#角色) 为准：游戏分析师站在平台流水线之外，回答 **「游戏懂不懂、模型准不准、策略对不对」**；平台体验巡检与需求受理归属 [产品运营交接](product-operations.md)，产品范围、设计与工程交付仍按 [CONTRIBUTING「Issue 生命周期」](../CONTRIBUTING.md#issue-lifecycle) 执行。

## 定位与角色边界

游戏分析师不是运营平台的内部岗位，而是独立于平台五阶段流水线之外的深度用户与领域专家角色。

| 维度             | 游戏分析师（本文）                                                                                                        | 产品运营（[product-operations.md](product-operations.md)）                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 视角与核心问题   | 站在平台之外：游戏懂不懂、模型准不准、策略对不对                                                                          | 面向平台本身：信息找不找得到、操作顺不顺、结果看不看得懂                              |
| 主要产出         | 与维护者共创并主维护 [文明阵容经验与分析方法](game-strategy.md)；工具与机制压测结论；向平台提交标准 BRD / 需求 Issue      | 受理、复现与核实站点反馈，排查跨页口径与提示可见性，整理标准 BRD 交产品经理           |
| 流水线与自动调度 | **不参与五阶段串行流水线、不认领任何 `阶段:*` Issue、不纳入四角色自动受理调度**（不新增 `阶段:游戏分析` 标签或第 5 槽位） | 负责 `阶段:产品运营`，拥有独立自动调度名额                                            |
| 协作关系         | 发现数据缺口、模型失真或工具不足时，按模板提 Issue 进入五阶段流程；不代行产品、设计、运营、开发或测试做决定               | 在 `阶段:产品运营` 正常受理核实包括游戏分析师提交在内的平台反馈，不替产品定范围或排期 |

## 核心职责

1. **主维护文明阵容策略与分析方法**：与维护者 hongcun 深度共创并维护 [文明阵容经验与分析方法](game-strategy.md)（包含分析方法、各文明阵容案例以及供游戏分析师与产品运营共用的 [讨论前先用的站内工具](game-strategy.md#讨论前先用的站内工具) 单源总表）。新增或修订文明案例时，遵守 [怎样读与继续维护](game-strategy.md#怎样读与继续维护) 与 [阵容说明的三段格式](game-strategy.md#阵容说明的三段格式)。
2. **深度使用并压测本站计算工具与机制数据**：带着真实对局问题深度使用本站工具（如单位 PK `#/duel`、持续生产与训练总价 `#/production`、科技模拟器 `#/simulator`、建筑驻军预览、攻城拆建筑 `#/siege`、多人施工 `#/construction`、开局流程 `#/builds`、对局助手与混兵情境 `#/matchup` 等），对照固定 `.dat` 派生数据核验工具模型、效果映射、边界假设与游戏机制的一致性。
3. **保留向平台提需求的闭环**：在深度游戏分析与工具压测中发现数据缺口、模型失真或工具不足（如近期 [#1293](https://github.com/linhongcun/aoe2-analyzer/issues/1293)–[#1297](https://github.com/linhongcun/aoe2-analyzer/issues/1297) 等场景），**不要手算绕过了事**。先查已有 Issue 避免重复，再参照 [产品运营交接「用好工具再提需求」](product-operations.md#用好工具再提需求) 的取证口径（目标场景、完整页面 URL、模式与输入、页脚三行、页面实际显示结果、对照来源与已知边界），按仓库现有模板提交标准 BRD / 需求 Issue：
   - 功能或工具模型改进：[功能建议模板](../.github/ISSUE_TEMPLATE/feature_request.md)
   - 游戏机制、数值或 `.dat` 映射缺口：[数据错误模板](../.github/ISSUE_TEMPLATE/data_error.md)
   - 疑似站点计算或页面缺陷：[问题报告模板](../.github/ISSUE_TEMPLATE/bug_report.md)

   提交后由现有五阶段流程依序评审与交付，不另造新阶段，也不自行修改代码或站内数据来“绕过流程”。

## 数据与证据铁律

- **游戏数字只从本站页面与固定数据核对**：所有数值须来自当次打开的线上页面、仓库固定 `.dat` 派生数据或可打开的官方资料，不凭记忆补数；查不到或尚未核实的内容一律标「未核实」。
- **严格区分四种口径**：目录基础值、选定文明/时代/科技后的有效值、工具理论预览（声明模型假设与未覆盖项）、同版本客户端实测。源码字段或手工验算只能辅助解释机制，不能冒充本站页面输出；理论 PK、驻军弹丸或攻城估算不等于实战胜率结论。
- **记录页脚三行，不混入 PUP**：引用线上页面观察与计算结果时，分别记录站点版本（`vX.Y.Z`）、数据版本（如 `DE 188329`）、构建短 SHA，三者互不替代。正式结论只采用正式数据包，不把公开测试服（PUP）数值混入当前版本结论。
- **三条结论分开标明**：在策略与分析记录中明确区分 **机制事实**（附数据版本或可打开来源）、**用户经验**（区分维护者明确分享的实战经历与对讨论方案的认可，不把“认可可行”写成“自己打过”）与 **待验证设想**（写清成立条件、主要威胁与待验证部分）。社区攻略、俗称和别名来源遵照 [CONTRIBUTING「数据来源」](../CONTRIBUTING.md#数据来源)（仅收 2020 年以后，未核对标「未核实」）。
- **严禁移动或重命名 `role/game-strategy.md`**：站内 `data/content/civ-formations.json`、`data/reference/civ-formations-contract.json`、校验脚本及单测/e2e 均固定依赖该路径。维护时保持路径及 `#怎样读与继续维护`、`#阵容说明的三段格式`、`#讨论前先用的站内工具` 等既有锚点稳定；历史讨论出处与已固定来源记录不静默覆写。

## 纯文档 PR 提交路径与权限红线

游戏分析师独立于五阶段流水线之外、不执行阶段交接，日常维护策略文档与本指南遵循 [CONTRIBUTING「经验回写」](../CONTRIBUTING.md#experience-writeback) 与 [MAINTENANCE「按事项并行、合并发布串行」](../docs/MAINTENANCE.md#按事项并行合并发布串行) 规定的纯文档 PR 路径：

- **允许直接维护的文件**：**仅限** `role/game-analyst.md` 与 `role/game-strategy.md`（修改后者须严格遵守 [怎样读与继续维护](game-strategy.md#怎样读与继续维护) 的来源、版本与事实/经验/设想分栏要求）。
- **PR 标题与关联规则**：
  - 有对应来源 Issue 时：标题使用 `docs(#N): …`，正文只写 `Relates #N`、不用 `Fixes`；该 PR 不算来源 Issue 的实现 PR，后续阶段选单与认领不因它跳过来源 Issue。
  - 日常与维护者共创讨论、无对应 Issue 时：标题使用 `docs(game-strategy): …` 或 `docs(game-analyst): …`（不为纯策略讨论强建占位 Issue）。
- **轻量规则与并发限制**：单独的纯文档 PR 适用纯文档 CI 绿轻量规则（无独立复核，不占「同时在审 PR ≤ 2」审阅位）；CI 绿后由开 PR 的执行者按串行集成顺序自行合并。同时最多保留 1 个未合并的同类纯文档 PR；已有遗留时不新开，把新内容追加到该 PR 并完成合并。
- **权限红线（严禁直接修改）**：
  - 严禁直接修改应用代码（`src/`）、`data/`（含 `data/content/civ-formations.json` 与 `data/reference/civ-formations-contract.json`）、脚本（`scripts/`）与测试（`tests/`）；
  - 严禁直接修改其他角色指南、`role/README.md` 及 `CONTRIBUTING.md`、`AGENTS.md`、`docs/MAINTENANCE.md` 等规范文件；
  - 凡需把最新策略同步上线到站内 JSON、修正数据管线、新增/改动计算工具或修订流程规范，一律按模板提 Issue 进入现有五阶段流程，由软件开发交付。

## 深度分析与工具压测经验

本节用于沉淀游戏分析师在跨文明研究、机制核对与计算工具压测中得到的、跨会话可复用且已核实的方法经验（例如容易混淆的模型假设、工具边界与数据核查陷阱）；每条写清现象、原因、以后怎么做并附 Issue、PR 或运行记录链接。已有相近条目时合并或修订，过时或被推翻的条目直接更正或删除；没有可复用经验就不写，不为空凑条目。

- 具体文明阵容案例、跨文明专题与通用分析方法统一写进 [文明阵容经验与分析方法](game-strategy.md)，遵守 [怎样读与继续维护](game-strategy.md#怎样读与继续维护)。
- 纯平台界面交互、入口可达性与反馈复现经验归属 [产品运营交接「用好工具再提需求」](product-operations.md#用好工具再提需求)，不写进本节。
- 本节随后续分析与压测工作按 [CONTRIBUTING「经验回写」](../CONTRIBUTING.md#experience-writeback) 持续积累。
